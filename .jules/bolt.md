## 2026-10-25 - Redundant API Calls in Dashboard Initialization
**Learning:** In `DashboardComponent`, `loadLancamentos` and `loadResumoMes` both independently call `contaService.getContasByMesReferencia(mesRef)`. During initialization (in the `effect`), they are called back-to-back synchronously. The cache in `ContaService` only caches resolved results. Thus, two identical Firestore queries are dispatched simultaneously because the first hasn't finished resolving to populate the cache before the second runs.

**Action:** We can optimize this by implementing a Promise-based cache or request coalescing in `ContaService`. This way, if a second request for the same `mesReferencia` comes in while the first is still in flight, it will return the same Promise, saving a redundant Firestore query.

## 2026-10-25 - Avoid Expensive Computations in Template @for Loops
**Learning:** In `DashboardComponent`, the template iterated over the `lancamentos` signal and called `getRowClass(item)` for every item. Inside `getRowClass`, it invoked `calculoService.calcularDiffDataVencimento(item)`, which instantiates `new Date()` multiple times. Because this function was evaluated directly in the template binding, it executed on *every* change detection cycle, creating unnecessary object allocations and severe layout rendering overhead for long lists.
**Action:** Always pre-calculate derived UI state. Map signals like `lancamentos` into a computed "view model" signal (e.g., `lancamentosView = computed(() => this.lancamentos().map(item => ({...item, rowClass: this.getRowClass(item)})))`) so the results are cached and recalculated only when the source data actually changes.
